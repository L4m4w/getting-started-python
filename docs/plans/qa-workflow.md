# План развития QA workflow для Niffler

Дата: 2026-11-13. Обновлено: 2026-11-14.
Статус: начата подготовка пилота и развитие harness; сквозной workflow не реализован.

## Цель

Построить workflow, который по изменению приложения определяет риски и
необходимое покрытие, предлагает тестовые сценарии, создаёт или обновляет
автотесты, запускает их и связывает результаты с Allure TestOps.

Для каждого изменения сохраняется цепочка:

**Требование → MR/PR разработки → сценарий → автотест → результат → MR/PR автотестов.**

Сначала человек проверяет сценарии и код. Автономность увеличивается после
оценки качества на реальных изменениях. Слияние изменений остаётся за человеком.

## Текущее состояние и предположения

- В этом репозитории есть UI-фреймворк Python + pytest + Selenium + Allure,
  Page Object, каталог переиспользуемых компонентов и локальный harness.
- Есть GitHub Actions и Jenkins. TestOps не подключён; наличие Allure-отчётов
  не означает наличие интеграции с TestOps.
- Репозиторий приложения, источник задач, платформа MR/PR и способ получения
  сборки приложения для конкретного commit ещё должны быть определены.
- Под TestOps в плане понимается Allure TestOps. Привязка к GitLab не обязательна:
  текущий тестовый репозиторий использует GitHub.
- API-тесты выбраны как предполагаемая область MVP. Готовность API-контрактов,
  клиентов и окружения проверяется до начала реализации.

## Целевой процесс

1. Получить событие MR/PR и зафиксировать версии приложения, тестов и требований.
2. Собрать diff, задачу, спецификацию, связанный код и существующие тесты.
3. Разделить ожидаемое поведение, фактическое изменение и расхождения между ними.
4. Определить риски, затронутые зависимости и существующее покрытие.
5. Предложить новые сценарии, изменения существующих и выбранную регрессию.
6. Проверить сценарии: источники ожиданий, дубли, полнота и открытые вопросы.
7. После ревью параллельно синхронизировать кейсы с TestOps и подготовить
   план автоматизации; затем объединить результаты и закрепить ID кейсов.
8. Создать или изменить тесты с переиспользованием компонентов фреймворка.
9. Выполнить проверки против нужной сборки, оценить падения и силу тестов.
10. Загрузить результаты в TestOps и создать или обновить draft MR/PR автотестов.
11. После согласования изменения обновить спецификации и опубликованную документацию.

## Контекст и поиск

Два логических корпуса:

| Контекст продукта | Контекст автоматизации |
| --- | --- |
| Код приложения, API-контракты, миграции | Автотесты, API-клиенты, Page Object |
| Требования, OpenSpec, история дефектов | Fixtures, данные, очистка, правила и CI |

Поиск объединяет точное совпадение символов и путей, семантический поиск и
переходы по зависимостям. Diff и непосредственно изменённый код передаются
напрямую. Фрагменты индексируются по смысловым единицам кода с метаданными:
репозиторий, commit SHA, путь, символ и диапазон строк.

Контекст MR/PR собирается на base/head SHA. При новом commit предыдущий анализ
помечается устаревшим. В MVP начинаем с точного поиска и выбранных примеров;
полную векторизацию добавляем после оценки недостающего контекста.

## Требования и документация

- Ожидаемое поведение берётся из задачи и согласованных требований.
- Код описывает фактическую реализацию. Восстановленная из кода спецификация
  считается черновиком с предположениями до проверки человеком.
- Расхождения требований и реализации фиксируются отдельно. Неоднозначный
  ожидаемый результат нельзя молча превращать в assertion.
- Целевое место версионируемых спецификаций — Git/OpenSpec рядом с кодом.
- Confluence — опубликованное представление согласованной документации со
  ссылкой на версию источника. Двустороннюю синхронизацию в первый этап не включаем.

## Роли и программные шаги

| Роль | Результат |
| --- | --- |
| Анализ изменения | Поведение, риски, зависимости и неизвестные |
| Проектирование сценариев | Новые/изменённые кейсы и выбранная регрессия |
| Проверка сценариев | Дубли, пропуски и неподтверждённые ожидания |
| Планирование автоматизации | Уровень теста, файлы, переиспользование, данные |
| Разработка тестов | Изменение кода по проверенному плану |
| Анализ результатов | Классификация падений с доказательствами |

Роли могут выполняться последовательно одним LLM-исполнителем. Отдельные агенты
вводятся по необходимости. Получение MR/PR, валидация данных, синхронизация
TestOps, запуск команд и создание MR/PR выполняются программными шагами.
Между этапами передаются структурированные артефакты по версионируемой схеме.

## Дорожная карта

| Этап | Работа | Критерий результата |
| --- | --- | --- |
| 1. Карта проекта | Источники, фреймворк, данные, CI и окружение | Известны входы и способ запуска |
| 2. Сквозной MVP | Один MR/PR, одна область, 1–2 теста | Выполнены критерии плана MVP |
| 3. Оценка на разных изменениях | Новое поведение, исправление, изменение покрытия | Собраны ошибки и объём ручных правок |
| 4. База знаний | Гибридный поиск и инкрементальная индексация | Качество контекста сравнено с базовым поиском |
| 5. Управление покрытием | Дубли, обновление тестов, подбор регрессии | Обоснован выбор создать/изменить/переиспользовать |
| 6. Спецификации | OpenSpec и публикация в Confluence | Требования и документация связаны с версией кода |
| 7. Расширение | Другие области, UI и межсервисные контракты | Подтверждена работа за пределами пилота |
| 8. Автономность | Возобновление, новые commit, ограниченные исправления | Workflow устойчив к повторам и сбоям |

## Надёжность и проверка качества

- Workflow сохраняет состояния этапов и возобновляется с места сбоя.
- Повторное событие не создаёт дубли кейсов, результатов или MR/PR.
- Прогон фиксирует SHA приложения и тестов, сборку/образ, окружение и артефакты.
- Генерация выбирает между новым тестом, изменением, параметризацией и
  использованием уже существующего покрытия.
- Проверяются подготовка и очистка данных, независимость и явные ожидания.
- Сила новой проверки подтверждается воспроизведением дефекта на старой
  реализации либо точечной мутацией, когда такой эксперимент применим.
- Падения различаются: продукт, тест, окружение, нестабильность. Исправления
  ограничены числом попыток и не ослабляют согласованные ожидания.
- Команды выполняются в изолированном runner; содержимое кода и документов
  рассматривается как данные, а секреты хранятся в окружении/credentials.
- Действуют правила [AGENTS.md](../../AGENTS.md), включая выбранный scope
  доступа к стенду и учёт постоянных записей регистрации.

## Метрики

Доля принятых сценариев и тестов, объём ручных правок, время ревью, количество
дублей, стабильность прогонов, способность обнаруживать целевые дефекты,
стоимость и время обработки MR/PR. После MVP фиксируем базовые значения и
используем их для выбора следующего этапа.

## Ближайшее действие

Выбрать пилотный MR/PR и проверить доступ к требованиям, исходникам приложения,
API-контрактам и сборке нужной версии. Реализация описана в
[отдельном плане MVP](qa-workflow-mvp.md).
