означает завершение ревью, генерации тестов или воспроизведения на приложении.

## Цель и границы

На одном реальном изменении пройти цепочку:

**MR/PR → контекст → сценарии → ревью → автотесты → прогон → TestOps → draft MR/PR.**

Предполагаемый scope: одна функциональная область и 1–2 API-теста. Текущий
репозиторий содержит UI-фреймворк: наличие готового API-слоя не предполагается.
До реализации проверяем контракты, доступный тестовый проект и способ запуска.
Если API-пилот требует отдельного фреймворка, фиксируем объём его подготовки
и согласуем scope; переход к UI-пилоту оформляем явным решением.

В MVP не входят полная векторизация, публикация в Confluence, автоматическое
согласование требований, массовая генерация тестов и автоматическое слияние.

## План работ

- [ ] **1. Выбрать пилот и источники.** Зафиксировать репозиторий приложения,
  MR/PR, base/head SHA, задачу, критерии приёмки и владельца ревью. Определить
  платформу разработки и репозиторий для автотестов.
- [ ] **2. Проверить окружение.** Определить, как получить сборку приложения
  из MR/PR и связать её с SHA, какие сервисы нужны, где выполняется прогон,
  какие данные создаются и как очищаются. Подтвердить границы доступа к стенду.
- [ ] **3. Описать фреймворк.** Использовать существующие AGENTS.md, knowledge
  и каталог компонентов; дополнить недостающие правила API-слоя. Определить
  эталонные тесты, clients/fixtures, assertions и команды запуска.
- [ ] **4. Собрать контекст.** Получить diff, окружающий код, задачу,
  спецификацию/контракт и связанные тесты. Сохранить источники и версии.
  Использовать точный поиск и выбранные примеры без обязательной vector DB.
- [ ] **5. Сформировать тестовый план.** Разделить ожидаемое и фактическое
  поведение; выделить риски, существующее покрытие, новые/изменённые сценарии,
  регрессию и открытые вопросы.
- [ ] **6. Провести ревью сценариев.** Проверить источники ожиданий, дубли,
  тестовые данные и проверяемость. Зафиксировать согласованную версию;
  неоднозначные ожидания разрешить до генерации соответствующего теста.
- [ ] **7. Подготовить реализацию и TestOps.** Выбрать файлы, компоненты и
  способ подготовки/очистки данных. Создать или связать кейсы в TestOps,
  сохранить стабильное соответствие scenario ID → TestOps ID. Эти две
  работы могут идти параллельно; ID закрепить до финального прогона.
- [ ] **8. Создать тесты.** В отдельной ветке написать или изменить 1–2 теста,
  используя план и правила фреймворка. Сохранить ссылки на сценарии и кейсы.
- [ ] **9. Проверить код и выполнить тесты.** Выполнить подходящие локальные
  проверки, затем прогон против нужной сборки. Сохранить команды, exit code,
  результат каждого теста и артефакты; разобрать ошибки подготовки отдельно.
- [ ] **10. Проверить силу теста.** Хотя бы для одного теста подтвердить
  обнаружение целевого дефекта/изменения на старой реализации, если совместима,
  либо через контролируемую точечную мутацию в отдельном окружении.
- [ ] **11. Опубликовать результат.** Загрузить Allure-результаты поддерживаемым
  инструментом TestOps, сохранить launch ID/ссылку. Создать draft MR/PR с кодом,
  описанием покрытия, версиями, результатами, ограничениями и ссылками.
- [ ] **12. Проверить повторный запуск.** Повторить обработку того же входа:
  обновить артефакты без дублей кейсов и MR/PR, не дублировать загрузку того же
  выполнения. Новый фактический прогон имеет отдельный execution ID.
- [ ] **13. Оценить MVP.** Зафиксировать ручные исправления, время ревью,
  проблемы контекста и следующие изменения общего плана.

## Минимальная реализация

Один оркестратор с последовательными этапами и сохранением состояния.
LLM выполняет анализ, проектирование и генерацию. Интеграции, запуск команд,
проверка схем и публикация выполняются программно. Несколько отдельных
агентов для MVP не обязательны.

| Артефакт | Минимальное содержание |
| --- | --- |
| Манифест запуска | Workflow ID, MR/PR, base/head SHA, SHA тестов, версия требований, окружение/сборка |
| Пакет контекста | Diff, найденные фрагменты, ссылки, версии, недоступные источники |
| Сценарии | ID, источники ожиданий, предусловия, шаги, результаты, данные, приоритет, уровень, покрытие, вопросы |
| Решение ревью | Версия сценариев, статус, замечания и исправления |
| План автоматизации | Файлы, переиспользуемые компоненты, данные, очистка, команды |
| Привязки TestOps | Scenario ID, TestOps ID, ссылка на кейс |
| Выполнение | Execution ID, версии, команды, exit code, результаты, Allure/логи, классификация падений |
| Итог | Ссылки на launch и draft MR/PR, ограничения и ручные правки |

Формат обмена — JSON по версионируемой схеме, материалы ревью — Markdown.
Расположение состояния и JSON-схем определяется при реализации; секреты,
сырые credentials и адреса с паролями в артефакты не включаются.

Состояния: `context_ready → scenarios_ready → awaiting_review → approved →
implementation_ready → executed → published`. Ошибки сохраняются с этапом
и причиной. Новый head SHA делает прежний анализ устаревшим и требует нового
анализа и ревью затронутых сценариев. Сбой TestOps не запускает повторную
генерацию кода. Число попыток исправления теста ограничивается до реализации
цикла; при исчерпании попыток сохраняются материалы для человека.

## Критерии готовности

- [ ] Пилот и версии всех входов зафиксированы.
- [ ] У сценариев есть источники ожидаемого поведения и результат ревью.
- [ ] Тесты встроены в выбранный фреймворк и соответствуют его правилам.
- [ ] Выполнен прогон против подтверждённой версии приложения из MR/PR.
- [ ] Есть доказательство силы хотя бы одного теста.
- [ ] Кейсы и результаты связаны в TestOps стабильными ID.
- [ ] Создан draft MR/PR с кодом и доказательствами проверки.
- [ ] Повторный запуск не создаёт дубли кейсов, MR/PR или загрузок выполнения.
- [ ] Зафиксированы ограничения и объём ручной доработки.

Сбор тестов, пропуск выполнения, старый отчёт или отсутствие доступа к сборке
не засчитываются как успешный сквозной прогон. Недоступная интеграция остаётся
невыполненным критерием, даже если остальные этапы проверены локально.

## Следующий эксперимент

После пилота проверить ещё несколько изменений: новое поведение, исправление
дефекта и изменение уже покрытой функциональности. Сравнить точный поиск с
семантическим на одинаковых входах по качеству найденного контекста и ручным
правкам. По результатам решить, какие части индексации и автономности развивать.
