## Что найдено

Приложение — Java 21 / Gradle, сервисы `niffler-auth`, `niffler-gateway`,
`niffler-spend`, `niffler-userdata`, `niffler-currency`, общий gRPC-модуль,
REST- и GraphQL-клиенты. Есть PostgreSQL, Kafka и конфигурации Docker Compose.

В main после исходного импорта приложения есть commit с Python UI-тестами
и его merge PR #1. В удалённых учебных ветках присутствуют более развитые
Python-тесты: API-клиенты, OAuth, модели, fixtures, доступ к БД и Allure.
Например, в `study_AL_14_kafka` есть `SpendsHttpClient` и API-тест категорий.
Это кандидаты на переиспользование; работоспособность и качество не подтверждены.

В просмотренной истории прикладной Java-код после импорта не менялся.
Изменения учебных веток относятся преимущественно к тестам; в последней
проверенной ветке также менялась конфигурация Kafka в `docker-compose.yml`.
Подходящий исторический change бизнес-поведения для API-пилота не найден.

У `niffler-spend` уже есть JUnit/MockMvc-тесты категорий и service unit-тесты.
Профиль `application-test.yaml` использует H2 и отключает автоконфигурацию
Vault/Flyway. Это потенциальный путь локальной проверки части сервиса,
но не подтверждение готовности всего окружения или Python API-прогона.

## Предлагаемый пилот: валидация переименования категории

Статическое наблюдение на main:

- В gateway DTO `CategoryJson.name` имеет `@NotBlank` и `@Size(min=2, max=50)`.
- `POST /api/categories/add` применяет `@Valid` к телу запроса.
- `PATCH /api/categories/update` принимает тот же DTO без `@Valid`.
- В `niffler-spend` обновление проверяет принадлежность категории пользователю
  и запрещённое имя `Archived`, но явной проверки длины/пустого имени в
  просмотренном `CategoryService.update` нет.

Это кандидат на учебный change, а не подтверждённый дефект: ожидаемое поведение
нужно согласовать независимо от реализации и проверить экспериментально.

Предлагаемое требование для ревью: при обновлении категории через публичный
REST API имя должно быть непустым, длиной от 2 до 50 символов. Невалидный запрос
должен возвращать HTTP 400 и оставлять прежние данные категории неизменными.
Проверка запрещённого имени и правила доступа сохраняются.

Предлагаемые первые сценарии:

1. Обновление имени на пустое или состоящее из пробелов: HTTP 400,
   прежнее имя сохранено.
2. Границы длины: 1 и 51 символ отклоняются; 2 и 50 принимаются.
   Для успешного изменения проверяется сохранённое значение.

Сценарии можно оформить как 1–2 параметризованных теста. Подготовка категории,
пользователя, авторизации и очистка данных должны быть описаны до прогона.
Проверка internal API, GraphQL и дополнительные правила доступа — отдельный scope.

## Следующие решения и действия

1. Согласовать предложенное требование и пилот либо выбрать другое изменение.
2. Выбрать место API-автотестов: текущий `getting-started-python` или существующий
   `niffler-tests-python` с явно выбранной учебной веткой. Автоматически переносить
   фреймворк между репозиториями не следует.
3. Зафиксировать отдельную версию требования и получить base/head пилотного change.
4. Подготовить первый пакет контекста и сценарии до реализации тестов.
5. Проверить способ изолированной сборки и запуска приложения из нужного SHA.
6. Определить проект TestOps и способ привязки кейсов/загрузки результатов.

При подготовке окружения учесть фактическую логику существующих
`docker-compose-dev.sh` и `docker-compose-e2e.sh`: они останавливают и удаляют
все обнаруженные Docker-контейнеры, а также образы с `niffler` в имени.
Для workflow требуется отдельный запуск с ограничением ресурсов проектом.
Эти скрипты при обследовании не выполнялись.
