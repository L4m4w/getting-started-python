## Требуемые исправления

1. P1 — tools/testops.py:cmd_verify. Существование launch не доказывает
   принятие результатов: launch создаётся до upload. Сейчас любой читаемый
   ID переводит failed/unknown/in_progress в uploaded; даже равенство ID
   запрошенному не проверяется. Нужна проверка проекта/launch и полного
   ожидаемого набора результатов и привязок. Если API этого не позволяет,
   оставить unknown и потребовать ручное подтверждение, не объявлять успех.
2. P1 — tools/testops.py:cmd_upload. Ненулевой upload exit автоматически
   получает failed и допускает --retry с созданием нового launch, хотя
   сервер мог принять часть batch. Успешный launch create с нечитаемым ID
   тоже помечается failed. Неопределённые и частичные внешние результаты
   должны блокировать слепой повтор; повтор существующего launch и попытки
   требуют явно определённой модели восстановления.
3. P1 — cmd_package/results.py. Между plan и package исходники результатов
   не сверяются с recorded digest, а build_package копирует неизвестные
   result JSON без блокировки. Добавленный после plan результат или
   повреждённый JSON может попасть в пакет мимо mapping. Нужна повторная
   полная валидация и identity перед package/upload; ошибки разбора,
   отсутствующий UUID и лишние результаты должны блокировать пакет.
4. P2 — CLI startup. Безопасно загружать корневой .env существующим
   python-dotenv, не переопределяя экспортированные значения. Проверить
   сценарии .env-only, exported precedence и отсутствие токена.

Для каждого исправления нужны содержательные offline regression tests.
Текущие 93 passed не закрывают эти контрпримеры; тест verify закрепляет
слишком слабое условие. Само разделение шести сценариев в копии результатов
проверено локальными тестами; серверное поведение ещё не подтверждено.
