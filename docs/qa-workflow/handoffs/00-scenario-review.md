## Подтверждено статически

- Gateway `CategoriesController.updateCategory` (`PATCH /api/categories/update`)
  не имеет `@Valid`; `addCategory` имеет. `CategoryJson` gateway содержит
  `@NotBlank` + `@Size(min=2, max=50)` на `name`.
- Gateway `GlobalExceptionHandler` обрабатывает `MethodArgumentNotValidException`
  и формирует `ErrorJson`; downstream `HttpClientErrorException` (включая
  400/404/406/409) пробрасываются с исходным статусом.
- Spend `PATCH /internal/categories/update` без `@Valid`, spend `CategoryJson`
  вообще без constraint-аннотаций, `CategoryService.update` проверяет только
  существование по `(username, id)`, запрет имени `Archived` (trim + ignore
  case) и лимит при разархивации. Проверки длины/пустоты нет.
- Следствие: на base все четыре невалидных имени (`""`, `"   "`, `A×1`, `A×51`)
  проходят downstream и сохраняются → ответ 200 вместо 400. Негативные случаи
  дают различие base/head; проверка силы выполнима.
- Каталога `niffler-gateway/src/test` в main нет — подтверждено.
- `settings.gradle` включает отсутствующий каталог `niffler-e-2-e-tests` —
  подтверждено; поведение Gradle не проверялось.
- Уникальный индекс БД на `(name, username)` для `category` (миграция V1,
  `ix_category_username`): переименование в уже существующее имя даёт
  `DataIntegrityViolationException` → spend 409 → gateway пробрасывает 409.
- `archived` в DTO — примитивный `boolean`: пропуск поля в теле PATCH означает
  `false` и может разархивировать категорию / запустить проверку лимита.
  Передача исходного `archived` из snapshot (scenarios.md, предусловие 5)
  корректно устраняет этот побочный эффект.
- Публичного endpoint удаления категории в просмотренных контроллерах нет
  (`DELETE` есть только для spends) — замечание scenarios.md о неопределённом
  способе очистки подтверждено.
- Gateway в профилях `local`/`docker`/`staging` — OAuth2 resource server,
  `/api/**` требует аутентификации; валидный JWT обязателен.
- У gateway есть `spring-boot-starter-validation` и `spring-boot-starter-test`
  — заявленный в assessment MockMvc-подход реализуем по зависимостям.

## Разделение MockMvc и реального PATCH/GET

Разделение в документах корректно и подтверждается кодом:

- Шесть обязательных случаев — только публичный REST через gateway;
  R3 доказывается только реальным сохранённым состоянием.
- MockMvc-эксперимент (api-framework-assessment.md) — отдельная
  диагностика уровня контроллера: доказывает HTTP-binding валидации и
  отсутствие вызова `SpendClient.updateCategory` при отказе; прокси для
  «данные не изменились» — `verify(..., never())`. Заменить e2e-проверку
  R3 он не может и не должен.
- Замечание для агента 04 (не блокер ревью): в standalone MockMvc регистрация
  `GlobalExceptionHandler` нужна только если проверять форму `ErrorJson`;
  для статуса 400 достаточно дефолтной обработки `MethodArgumentNotValid`.
  Валидатор на classpath есть (validation starter подтверждён).

## Замечания (все minor; меняют детали реализации, не ожидания)

- **M-1, затрагивает CAT-UPD-VAL-001…004**: в
  `test_update_category_rejects_invalid_name` проверка статуса (шаг 3) идёт
  до повторного чтения (шаги 4–5). На base прогон остановится на assertion
  статуса и не даст артефакта «невалидное имя сохранено», хотя именно это
  сильнейшее доказательство различия. Предложение: повторный GET выполнять
  безусловно до assertions (или собирать snapshot и прикладывать к Allure),
  затем проверять `HTTP 400` и неизменность snapshot. Ожидания не меняются,
  изменяется только сбор evidence. Альтернатива — оставить порядок как есть:
  различие по статусу уже достаточно для strength-check.
- **M-2, затрагивает CAT-UPD-VAL-005/006**: шаг 3 позитивного теста
  проверяет `id/name` в теле ответа PATCH. Это проверка текущего контракта,
  выходящая за R4 (сохранённое состояние). Предложение: оставить, но пометить
  как вторичную contract-проверку — её падение без расхождения состояния
  означает изменение формата ответа, а не нарушение R4. В новое требование
  не превращать.
- **M-3, затрагивает предусловие 3 и CAT-UPD-VAL-005/006**: целевые имена
  позитивных случаев — фиксированные строки (`AA`, `A×50`), а БД имеет
  уникальный индекс `(name, username)`. Оставшаяся от прошлого прогона
  категория с таким именем превратит ожидаемый 200 в 409 и даст ложный
  результат. Предложение: кроме запрета дубликатов в предусловии 3 явно
  проверять перед PATCH отсутствие целевого имени у пользователя
  (понятная ошибка предусловия вместо 409), и зафиксировать очистку
  строго по `id` — категории, получившие на base невалидные имена
  (`""`, `"   "`), нельзя надёжно искать по имени.

## Нерешённые вопросы

Блокируют написание тестов (контракт fixtures; тела тестов можно писать против
абстрактных фикстур уже сейчас):

1. Размещение и транспорт API-тестов: предложение `tests/api/` +
   `infrastructure/http/` + явный HTTP-клиент в `requirements.txt` из
   assessment пока не подтверждено. Нужно решение координатора.
2. Способ получения JWT для выделенного пользователя (предусловие 2
   scenarios.md). Варианты: (a) программный OAuth code+PKCE против
   niffler-auth изолированного окружения — максимально честно, но клиент
   в учебном проекте признан нерабочим и требует переработки;
   (b) токен из секретов окружения — быстро, но привязано к сроку жизни
   токена; (c) тестовая конфигурация JWT decoder — меняет окружение.
   Рекомендация: определить после входа агента 03, тесты писать против
   фикстуры, возвращающей `token`, без привязки к механизму.
3. Способ подготовки категории и очистки (предусловия 3, cleanup-блок
   scenarios.md). Рекомендация: создание через `POST /api/categories/add`
   (публичный путь; на base он уже с `@Valid`, значит исходные имена
   фикстур должны быть валидными — тривиально выполнимо), очистка —
   удаление по `id` в БД spend либо пересоздание данных стенда; выбор
   зависит от доступа к БД, отдаётся агенту 03. Архивация очисткой
   не считается — согласно scenarios.md.

Блокируют только запуск окружения/прогон, не написание тестов:

4. SHA-привязанная изолированная сборка полного стека
   (gateway+spend+auth+PostgreSQL) с доступным gateway URL; существующие
   compose-скрипты с глобальной очисткой Docker не подходят без переработки.
5. Выделенный пользователь и его секреты на этом окружении
   (общий публичный аккаунт исключён сценариями).
6. Проверка сборки Gradle: отсутствующий модуль `niffler-e-2-e-tests`,
   доступность зависимостей и wrapper — задача агента 01/02.
7. Head SHA пилотного изменения (нужен для head-прогона; base-прогон
   и написание тестов возможны без него).
8. TestOps ID — учётная задача при синхронизации.
