## Решения по 19A

1. Состав приложения: два предложенных файла — только @Valid production
   fix и Java-регрессия; новых правок приложения в 20 нет.
2. Состав QA: принять 42 файла как предварительное ядро. Добавить
   requirement/scenarios/mapping, реализацию workflow и необходимую
   документацию/исторические материалы, на которые опираются новые runbook
   и ссылки. Процессные материалы выделить в отдельный логический commit
   внутри QA PR; их не удалять. Сырые логи и artifacts не включать без
   точного allowlist и проверки секретов; для исключённых локальных
   evidence явно обозначить недоступность из удалённого PR.
3. Планировать узкий QA PR от текущей базы MVP_workflow, отдельную
   feature-ветку; не заявлять, что это PR всего отличия от master.
   Свежая удалённая base/права записи проверяются перед будущей публикацией.
   Текущий checkout и index не менять. Это локальный план, не разрешение Git writes.
4. После 20/21 пакет актуализировать: 19A не является финальным составом
   и не содержит нового immutable head. Команды публикации из handoff
   иллюстративны; будущий gh body передавать через подготовленный файл.

## Обязательные уточнения 19B для реализации 20

1. **Идентичность и index.** Не lowercase весь URL/локальный путь:
   сохранять регистр значимых path-компонентов, нормализовать известные
   transport/host/.git формы явно. Index ключ — repo+pilot, а не pilot
   один. Изменение repo/base/ID не обходит историю intent/execution/PR.
   Supersede сохраняет ссылки/незавершённые intents и не разрешает resend.
   Digest dirty tests требует детерминированного allowlist source snapshot,
   включая untracked; null допустим только до gate, которому identity нужна.
2. **Глобальная блокировка и запись.** Нужна index lock, независимая от
   workflow lock. Порядок index → workflow → delegated execution; index
   lock не держать во время внешних subprocess. Уникальный workflow lock
   не сериализует запись общего index. При сбое между index/state записи
   должен быть recoverable intent/протокол: нельзя терять запись либо
   тихо создавать параллельный lineage. Новый state сначала валидировать,
   затем temp+flush/fsync+replace; при заявлении устойчивости к потере питания
   синхронизировать и каталог. Atomic replace не равен общей транзакции.
3. **Возобновление execution.** `run-execution` тоже имеет durable intent
   до subprocess и связь с evidence. Неизвестный исход прогона не запускает
   новый pytest автоматически. Нельзя выбирать «последний run» в artifacts.
   При утрате доказуемой связи — blocked, не повтор. `resume` реализуется
   как явная команда; T10 не означает безусловный retry любого эффекта.
4. **PR reconciliation.** Ноль результатов поиска после unknown/dispatched
   create, даже свежего, не доказывает отсутствие записи/задержки индексации.
   Такой intent остаётся blocked/unknown. Create допустим при первом
   доказанно не отправлявшемся намерении после полного свежего поиска;
   найденное единственное точное совпадение — adopt, конфликт/неполный
   поиск/несколько совпадений — blocked. В 20 live PR transport отсутствует.
   Учитывать отдельные PR приложения и QA как required entries, не один
   взаимоисключающий repo=tests|app. Без реальных verified PR полного published нет.
5. **Приёмка артефактов.** Markdown связывается с versioned JSON envelope
   (IDs/requirement coverage/node IDs/review/scenario digest). Свободный
   текст и переданный exit_code=0 не заменяют проверки схемы/файлов и
   реально выполненные compile/list. Actor — только declared human/llm/
   orchestrator/imported, не аутентифицированная личность; approved —
   явное принятое решение, не автоматический вывод из actor.
   Все изменяемые inputs/requirements/source/env/bindings входят в
   dependency digests. Gate пересчитывает их, а не доверяет bound_revision.
6. **Инвалидация и публикации.** По умолчанию новый head/patch требует
   нового context и повторного ревью затронутых сценариев; совпадение
   Markdown само по себе не сохраняет прежнюю approved. Unchanged source
   scopes могут сохранять evidence только при доказуемой equivalence,
   с явной старой provenance. PR spec/head и публикации тоже ревизионные.
   Strict schema не принимает заглушки из примеров 19B за валидные SHA.
7. **Политика пилота.** Required head/fix execution — шесть passed;
   доказательство силы — отдельный обязательный evidence gate, допускающий
   импорт принятого red baseline (4 ожидаемых failures, не общий all-pass).
   Baseline и API/TestOps заново не запускать. require_pr=true для полного
   MVP, при отсутствии PR фаза максимум executed/blocked. App head сейчас
   kind=patch, а не none. Новые fixtures — синтетические корректные примеры,
   старые JSON/evidence 19B не исправлять.
8. **Область 20.** Без live PR/TestOps/SUT writes; программные adapters и
   fake transports проверяют реальное выполнение и crash boundaries.
   Live transport PR — будущая разрешённая работа, offline успех его не
   заменяет. Исторический execution импортируется read-only с точной
   проверкой источников/состава/пакета, без изменения его state.
