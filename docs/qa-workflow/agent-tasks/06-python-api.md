## Действия

Реализуй два параметризованных теста для шести согласованных случаев.
Негативные: PATCH → 400 → GET → snapshot не изменился. Позитивные:
PATCH → 200 → GET → новое имя и сохранённые остальные поля.

Выдели минимальный HTTP-слой, fixtures авторизации/данных/cleanup.
Проверяй статус до преобразования успешного ответа. Один вызов метода клиента
должен делать ровно один HTTP-запрос. Не копируй целиком учебный framework,
ORM, browser fixtures, проблемный PKCE или Allure-helper с двойным запросом.
Зависимости добавляй явно и минимально; не полагайся на транзитивные пакеты.

## Проверка и передача

Проверь офлайн transport-сценарии на подменах, включая отрицательный ответ и
отсутствие повторного запроса, затем collection и подходящие unit-тесты.
Не обращайся к общему аккаунту/публичному стенду и не создавай данные без
готовности окружения. Отсутствие token/cleanup — ошибка подготовки, не fake PASS.
Новая api-группа harness должна требовать явного разрешённого SUT scope.

Создай `docs/qa-workflow/handoffs/06-python-api.md`: команды, результаты,
импорты компонентов, конфигурация без секретов и оставшиеся блокеры для 07.
Офлайн unit-проверки не засчитывай как выполненные сценарии API.
